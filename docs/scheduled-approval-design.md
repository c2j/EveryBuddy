# 设计文档：每日「计划-审批-派发」自动化

状态：P1–P3 核心已实现（本地汇总、审批队列、串行派发、超时合并） · 日期：2026-10-31
未做：通知上的三个动作按钮、微信/企微、低风险免审批、Git/飞书、并发 3。ACP 仍是单会话，派发串行且会等当前 ACP 回合结束。
配套 UI 设计稿：[scheduled-approval-ui-mockup.html](scheduled-approval-ui-mockup.html)
前置研究：[workbuddy-scheduled-module.md](workbuddy-scheduled-module.md)

## 1. 背景与目标

用户希望：**每天 8:30 自动总结前一天所有 Agent 的任务完成情况，对照计划梳理形成今天的任务，提示用户；用户同意后，安排对应 Agent 实施。**

这是一个 AI 版每日站会自动化。价值在于：

- 聚合成本高：昨日多个 Agent 的产出散落各会话，人工汇总费时
- 节奏契合：8:30 在工作开始前送达"昨日报 + 今日计划"
- 补全闭环：当前任务均由用户逐个发起，缺少"计划 → 确认 → 批量派发"的管理层动作

对照 WorkBuddy Scheduler 能力（见前置研究）：定时、汇总、计划、通知四环可直接实现；**"同意后派发"的双向审批是硬缺口**，WorkBuddy 推送单向、后台运行无审批 UI，需在 EvoBuddy 侧原生实现 approval-gated 任务类型。本设计即该扩展。

## 2. 一句话定义

在现有 Scheduled 模块上新增第 4 种调度模式 **「计划-审批-派发」**：到点运行一次"汇总提示词"生成结构化计划 → 计划进入**待审批队列**并通知用户 → 用户批准（全部/挑选）→ 批准的任务按模板派发为后台会话 → 执行结果回流，成为次日的"昨日总结"数据源。

流程：

```
配置一次 → 每天 8:30 汇总 → 生成计划 → 通知审批 → 批准 → 派发执行 → 结果回流
```

### 3.2 屏 2：创建/编辑弹窗（功能定义入口）

> 实施状态（PR #39 + 调度迭代）：创建对话框已升级为原型的四宫格模式选择器——
> 一次性 / 周期 / 间隔 / 计划-审批-派发 ✅；周期档支持 每天/每周/双周/每月/每年
> + 星期多选（周/双周）+ 月内日（月）+ 月份（年）✅（数据模型 `Periodic`，创建周锚定双周奇偶）；
> 计划档含 时间/常驻任务/提示词模板/审批截止 ✅；头部 `Daily plan` 按钮复用同一对话框（预选计划档）✅；
> 汇总范围 ❌（固定"昨日全天"）；执行 Agent / 工作区 / 并发选择 ❌（派发固定跟随来源、串行）；
> 推送开关 ❌；低风险免审批 ❌；超时后策略 ❌（固定合并）

调度模式新增第 4 项「计划-审批-派发」，选中后展开四块配置：

**a) 执行时间与完成判定** —— 复用现有周期配置（每天 08:30）；完成判定依据（见 §4.4）。

**b) 汇总范围**（见 §4）—— 定义"昨日总结"看什么：时间窗口、会话来源、外部数据源。

**c) 计划任务模板** —— 计划中的每条任务按此派发：

| 字段 | 说明 |
|---|---|
| 执行 Agent | 派发使用的 agent/专家；默认"跟随来源任务" |
| 工作区 | 默认跟随来源任务的工作区；可固定 |
| 并发上限 | 同时派发的会话数（默认 3） |
| 提示词模板 | 支持 `{task.title}` `{task.context}` `{task.done_when}` 占位符 |

**d) 审批与超时策略**

| 项 | 默认值 | 说明 |
|---|---|---|
| 桌面通知 | 开 | 计划生成后立即提醒 |
| 推送微信/企微 | 开 | 不在电脑前也能看到计划（单向，仅供知情） |
| 低风险免审批 | 关 | 符合风险规则的任务自动派发，不经确认 |
| 审批截止 | 生成后 45 分钟 | 到点未处理触发超时策略 |
| 超时后 | 跳过并合并到明日计划 | 备选：直接跳过 / 全部自动执行 |

### 3.3 屏 3：审批交互

> 实施状态（PR #39）：审批卡片全要素（倒计时/summary/diff/勾选/来源标注）✅；
> `改`按钮 ✅（仅提示词）；批准所选/全部/跳过 ✅；通知动作按钮 ❌；风险点 ❌；保存为模板偏好 ❌

- **系统通知极简闭环**：通知上直接提供三个动作——`全部批准` / `查看并挑选…` / `跳过`，不打开主窗口即可完成
- **计划详情**（点开或从队列进入）：
  - 逐条任务：来源说明（基于昨日哪个会话 / 计划哪条）、风险点、`改`按钮微调 Agent/工作区/提示词
  - 底部计划 diff：相对本周计划的新增/移除/落后加塞
  - `批准 N 项并派发`；`保存为模板偏好`（把本次微调记忆为默认）

### 3.4 屏 4：派发后与回流

> 实施状态（PR #39）：运行记录页（状态/resolution/diff/逐条状态/Open 跳转会话）✅；
> 日期分组/时长列/类型筛选/归档 ❌；并发上限 ❌（ACP 单会话，串行=1）

- 批准的任务成为可见后台会话（运行中/排队，受并发上限约束），可点开
- 明日 8:30 汇总自动包含：审批任务的执行结果 + 范围内其他会话 → 完成率、超时原因、建议顺延项
- **数据闭环**：审批记录与派发来源一并落库，次日对照有据可查

## 4. 汇总范围定义

汇总范围回答三个子问题：**看哪些时间、看哪些会话、以什么为准判定完成。**

### 4.1 时间窗口

| 预设 | 窗口 | 适用 |
|---|---|---|
| 昨日全天（默认） | 昨日 00:00 – 今日执行时间前 | 固定作息；右端跟随执行时间，8:00 后的新会话归属今天 |
| 最近 24h | 滚动窗口 | 非固定作息 |
| 自定义 | 起止各自设置 | 补跑、特殊节奏 |

### 4.2 会话来源（多选）

- ☑ 所有后台会话（含用户手动发起）——默认，总结完整
- ☑ 仅 Scheduled 运行——只看定时任务自身 runs，噪音小
- ☐ 指定工作区 / Agent——进一步收窄（如只统计某项目的执行类 Agent）

设计取舍：默认"所有后台会话"更完整（手动干的活也算昨日产出），代价是噪音；允许按工作区排除来降噪。

### 4.3 外部数据源（连接器，开关式）

| 数据源 | 用途 |
|---|---|
| Git 提交 | 验证代码类任务"真的落了提交" |
| 飞书任务 / PM 工具 | 同步外部排期做计划对照 |

不开启时纯用本地会话记录，零配置可用；开启后完成判定更硬。

### 4.4 完成判定依据（可多选）

- 会话终态（正常结束 / 中断 / 出错）——默认
- 有产物（artifact/文件变更）
- 有 Git 提交
- 用户手动确认

判定越严，与"低风险免审批"联动越要求准确性；严格判定适合配高风险任务必审。

## 5. 数据模型（概念层）

```text
PlanRun           一次计划运行：plan_task_id, run_at, scope_snapshot,
                  summary(昨日总结), items[PlanItem], status(待审批/已批准/超时跳过/部分批准)
PlanItem          单条计划任务：title, source(昨日未完成|计划新增|模板建议),
                  agent, workspace, prompt, risk(高|低), approved(bool), dispatch_session_id
DispatchSession   派发的后台会话：session_id, plan_item_id, status, result  ← 回流数据源
```

派发的会话与普通会话同库记录（复用现有任务记录），保证次日汇总可读。

## 6. 关键行为语义

1. **审批是守门，不是阻断执行主体**：汇总与计划生成本身不需要审批（它只读）；只有"派发执行"被审批拦住。
2. **超时不静默**：过期计划保留在队列中显示处理结果；合并到明日时在 diff 中注明"昨日顺延"。
3. **部分批准**：只派发勾选项，未选项按"跳过"处理并可手动再派发。
4. **微调记忆**：详情里点"保存为模板偏好"把 Agent/工作区/提示词微调写回任务模板。
5. **幂等**：同一 PlanItem 不会重复派发（派发后锁定 session_id）；重复点击批准去重。

## 7. 待商榷（开放问题）

1. **风险分级规则**：模板内置（如"仅新增文档=低风险"）还是用户逐任务标注？或两者结合（内置规则 + 用户可覆盖）？
2. **超时默认策略**：跳过、合并到明日、还是对低风险自动执行？影响默认值选择。
3. **是否允许"定时不审批"直跑变体**：高信任例行任务完全绕过审批，作为同模式下的开关还是独立模式？
4. **会话来源默认值**：所有后台会话 vs 仅 Scheduled 运行，哪个做默认？
5. **通知通道优先级**：桌面通知与微信推送是否需要"谁优先响应以谁为准"的去重语义？
6. **计划生成失败的降级**：汇总运行失败/网络不可达时，是否仍推送一条"昨日总结不可用"占位提醒？

## 9. OS 集成与 Daemon 演进（两步走）

调度器目前只活在 GUI 进程里（5s 轮询），应用关闭即停摆。本节定义补齐
"应用未开时谁来跑"的两阶段方案：**先 P1 验证使用模式，再决定是否进入 P2。**

### 9.1 P1：headless 子命令 + OS 定时器（无新进程模型）

给 `evobuddy` 增加 headless 子命令，不建 GTK、跑完即退：

```text
evobuddy schedule --run-due   # 执行一次 tick：生成到期计划、过期收敛、
                              # 把已批准条目标记为待派发（不启动会话）
```

语义约定：

- headless 运行**不派发会话**（`Runner`/ACP 在 GUI 进程），只推进
  `scheduled.json` / `plans.json`；用户下次打开 GUI 时由现有
  `pump_dispatches` 补拉起
- 审批仍回到 GUI 待审批队列；headless 可选发一条桌面通知提示"计划已生成"
- **单写者约束**：headless 与 GUI 不应同时写状态文件。实现是 `schedule.lock`
  上的排他锁，包住 `scheduled.json` / `plans.json` 的一次完整读改写。
  `tasks.json` 只读；读到的内容不是合法 JSON 时本次直接退出，不生成计划

三平台注册方式：

| 平台 | 登录自启（GUI 兜底） | 定时调起 headless |
|---|---|---|
| Linux | XDG Autostart `~/.config/autostart/evobuddy.desktop` | systemd user timer：`OnCalendar=*-*-* 08:30:00` + `evobuddy-plan.service` |
| macOS | LaunchAgent `~/Library/LaunchAgents/com.evobuddy.plist`（`RunAtLoad`）；分发版用 SMAppService | launchd `StartCalendarInterval` 08:30；休眠唤醒后的补跑语义需实测 |
| Windows | Startup 文件夹 / `HKCU\...\Run` | Task Scheduler 每日 08:30 + "missed start 尽快补跑"（`schtasks /sc daily /st 08:30`） |

测试/CI 配套（跨平台差异封装）：Linux 用 `xvfb-run`；macOS 需真实 GUI
session、无 `timeout` 命令（用 `perl alarm` 或后台+kill）、产物在 `$TMPDIR`
而非 `/tmp`；Windows 需 MSYS2 GTK3。selftest 已内置 12s 超时兜底，外部
timeout 仅作双保险。

### 9.2 P2：常驻 Daemon（正确终态，按需启动）

仅在 P1 验证后确认需求真实存在时进入。架构要点：

- **单一写者 = daemon**：三个状态文件只由 daemon 写；GUI、CLI、未来托盘都是
  IPC 客户端（Unix socket / named pipe，协议从简）
- **`Runner`/ACP 移入 daemon**（或拆出无 GTK 的 `eb-core`）：派发会话真正
  脱离 GUI 生命周期；该拆分同时改善可测试性
- **权限桥跨进程**：dispatched 会话的预批准在 daemon；交互式权限转发 GUI 弹窗
- **通知升级**：daemon 内做桌面通知与微信/企微推送（§3.2-d 的推送开关届时落点）

| 平台 | 常驻方式 |
|---|---|
| Linux | systemd user service（`WantedBy=default.target`） |
| macOS | LaunchAgent（`KeepAlive`）或菜单栏托盘 |
| Windows | 登录触发的计划任务常驻，或系统托盘 |

### 9.3 进入 P2 的判定条件

满足任一条再启动，避免为 10% 的收益付 90% 的重构成本：

1. P1 使用后"应用没开导致审批/派发延迟"成为实际抱怨；
2. 出现无 GUI 机器（服务器/CI）也要跑计划任务的需求；
3. 需要微信/企微推送且要求应用未开也能送达。
